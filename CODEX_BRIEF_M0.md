## 1. What the project is, in five lines

Semantic Operation Continuity (SOC) studies how to keep decisions intact when several AI agents share one long task. The task here is translating IETF security RFCs from English into Turkish with triads of Claude, GPT and Gemini agents. Every accepted decision (for example "access token is rendered as *erişim belirteci*") becomes a **commitment** in a versioned **ledger** that belongs to the task, not to any model. The main experiment asks whether that ledger keeps decisions through a model replacement and a brief change better than a strong retrieval-based workflow. M0 builds the ground everything else stands on: the repository, the episode data format, the RFC segmenter, the ledger core and the commitment schema.

## 3. Fixed technical decisions

| Area | Decision |
|---|---|
| Language | Python 3.12 |
| Tooling | `uv` for environments and locking; `pytest`; `Ruff` for lint and format; `mypy --strict` on the core packages; `import-linter`; `Hypothesis` for property tests |
| Ledger store | One SQLite file per run, in WAL mode. An append-only event table with a hash chain. Projections are rebuilt from events and are never written directly |
| Compare-and-set | One `BEGIN IMMEDIATE` transaction per write. SQLite serializes writers; rely on that, do not build your own lock |
| Commitment schema | A small **hand-written** ontology. Each commitment and each version is a JSON-LD record using PROV-O terms. SHACL shapes, run with `pySHACL`, validate every ledger write inside the write transaction |
| Schema libraries | `rdflib`, `pyshacl`, `pydantic` |
| Sentence identity | Every source sentence gets a stable ID such as `9700-4.2-s03` (RFC number, section number, sentence index) |
| CI budget | The every-commit suite runs with no network in under five minutes |
| Coverage | At least 90% branch coverage on the core packages (`soc/ledger`, the episode package code, the segmenter) |

The ontology must not be generated by a model or inferred from data. It is written by hand, reviewed, and later frozen.

### 4.2 Episode package format and validator

An episode is a frozen, hashed directory under `data/episodes/<episode-id>/` holding exactly seven files.

| File | Content |
|---|---|
| `source.jsonl` | One line per sentence: stable ID, section, text, and the scope keys it touches (terms, BCP 14 key words, numbers) |
| `brief.yaml` | The written client brief, with an ID per clause, so evidence can cite `brief:B7` |
| `hidden.yaml` | About five unwritten client preferences. **Evaluation data** |
| `seeds.jsonl` | Seeded test items: type, sentence IDs, expected answer, and the kind of correctness tested (source fidelity, client preference, commitment continuity). **Evaluation data** |
| `events.yaml` | The chunk after which the executor changes; the brief change, the two or more decisions it revises, and its chunk; the points where approved decisions arrive; the planted-error schedule |
| `affected.jsonl` | For each revised decision, the chunks and use sites it truly affects. **Evaluation data** |
| `manifest.json` | A SHA-256 hash of every other file |

Build:

1. **Typed models** for every file (Pydantic), with a documented schema.
2. **Two loaders.** A runtime loader under `soc/` that exposes only `source.jsonl`, `brief.yaml` and the event schedule *without answers*. A full loader under `eval/` that reads everything. The runtime loader must be unable to return `hidden.yaml`, expected answers or affected sets.
3. **A validator** (a CLI command and a function) that checks, from the package alone and without running anything:
   - every manifest hash matches;
   - every sentence ID is unique and well-formed, and every ID referenced by another file exists;
   - every brief clause ID referenced exists;
   - event positions fall inside the episode's chunks, with the executor change before the brief change;
   - the **coverage rule**: at least five approved decisions are used on both sides of the executor change, and the brief change revises at least two decisions used on both sides of it — one a term, and one that is non-lexical or scope-limited.
4. **One toy episode** as a fixture: a few sections, hand-written, enough to pass the validator. Plus deliberately broken copies, one per validator rule, each of which must fail with a message naming the rule.

*Your choice:* the exact field names, and how a decision is tagged as `term`, `non_lexical` or `scope_limited`. Document them; they will be frozen later.

### 4.3 RFC segmenter

Under `soc/tasks/`. Turns an RFC's XML (the `xml2rfc` v3 format published by the RFC Editor) into the `source.jsonl` sentences.

- **Stable IDs.** `<rfc>-<section>-s<nn>`, deterministic: the same input always yields the same IDs.
- **Verbatim blocks.** Source code and artwork are kept as single segments, byte-for-byte, and marked non-translatable.
- **Scope keys per sentence.** BCP 14 key words *only when in capitals* (MUST, MUST NOT, REQUIRED, SHALL, SHALL NOT, SHOULD, SHOULD NOT, RECOMMENDED, NOT RECOMMENDED, MAY, OPTIONAL); numbers; and glossary terms from a supplied list.
- **Round trip.** Joining the segments of a section reproduces that section's source text exactly.
- **Sentence splitting** must survive the usual traps: "e.g.", "i.e.", "Section 4.2.", version numbers, URLs, and sentences ending inside parentheses.

Use RFC 9700 (OAuth 2.0 Security Best Current Practice) as the real test input. Check a copy of its XML into the test fixtures, with the IETF notices intact, so tests need no network.

### 4.4 Ledger core

Under `soc/ledger/`. This is the centre of the milestone.

**Event table — fixed columns:**

`seq`, `event_id`, `run_id`, `time`, `type`, `actor` (agent, model, role), `commitment_id`, `base_version`, `new_version`, `ledger_version`, `chunk_id`, `payload` (JSON), `prev_hash`, `hash`.

**Event types** (define all now, so the log format is stable; only the ones marked M0 need behaviour):

| Type | M0 behaviour |
|---|---|
| `Ratified` | **Yes.** Applies only if `base_version` is the commitment's current version |
| `ConflictRaised` | **Yes.** Emitted when a compare-and-set fails; carries expected and actual version |
| `Revised`, `Superseded`, `Revoked` | **Yes.** State changes with old and new version, owner, reason |
| `Tombstoned` | **Yes.** Emitted when a rendering is superseded: rendering, scope, commitment, version |
| `BriefChanged` | **Yes.** Only an actor with the principal role may emit it |
| `ChunkBuilt` | **Yes, storage only.** Records ledger version, commitment IDs and versions used, and the decisions delivered in the prompt |
| `ExecutorRebound` | **Yes, storage only.** Old and new model, ledger version at handover |
| `FlagRaised`, `DecisionDeclared`, `DecisionCaptured`, `CrossExamTurn`, `VoteCast`, `StaleMarked`, `GateDecision`, `PrincipalAnswered`, `StandingUpdated`, `SanctionApplied` | Type and payload model only |

**Rules — fixed:**

1. **Append-only.** No update or delete on the event table, enforced in the database as well as in code.
2. **Hash chain.** Each event's `hash` covers its content and `prev_hash`. A verifier walks the chain and reports the first break.
3. **Compare-and-set.** A ratification names the version it read. If that version is still current, the event applies and the commitment's version rises by exactly one. If not, **nothing is overwritten**: a `ConflictRaised` event is written instead. Recency never decides.
4. **Versions rise by one and never repeat.** A database constraint, not only a check in code.
5. **Tombstones.** Superseding a version tombstones its rendering. A lookup `is_tombstoned(rendering, scope)` answers from the projection.
6. **Authority.** `BriefChanged` from any actor without the principal role is rejected. A revision of a ruling is rejected unless the actor is that commitment's owner.
7. **Projections** — current commitments, versions, usage records, tombstones and chunk states — are derived from events. A `rebuild()` replays the log from empty, and its result must equal the live projections exactly.
8. **Monotonic reads.** A reader can ask for "the commitments in scope S at ledger version V", and V never goes backwards for a given reader handle.
9. **Crash safety.** A writer killed mid-transaction leaves no partial event. On reopen, the chain is intact and no update is lost or duplicated.

*Your choice:* the table DDL beyond the fixed columns, the projection storage, and the Python API. Keep the write API small; the review will ask why each public function exists.

### 4.5 Commitment ontology and SHACL shapes

Under `soc/ledger/schema/`: the ontology in Turtle, the shapes in Turtle, a JSON-LD context, and fixtures.

**Concepts — fixed:**

| Concept | Meaning |
|---|---|
| `Commitment` | Stable identity; the operation it belongs to; its owner, who alone may revise it; debtor and creditor |
| `CommitmentVersion` | An **immutable** version. Holds the fields below |
| `ExecutorEpoch` | An interval during which one model executed the operation on the debtor's behalf |
| `RevisionEvent` | An activity linking an old and a new version, with its sequence and the approving actor |
| `Ratification` | An activity that made a version binding: consistency level, evidence, ratifier |

**Fields of a `CommitmentVersion` — fixed:** scope; the rendering or reading; a **verbatim source quote** with the sentence ID it comes from; a **checkable rule** (a typed record: rule kind plus parameters — the checker that runs it is a later milestone, M0 only fixes the data shape); rationale; evidence (citations of source sentence IDs, brief clause IDs or other commitments); proposer; ratifier; consistency level (`ONE`, `QUORUM`, `ALL`, `SERIAL`); state (`proposed`, `provisional`, `ratified`, `contested`, `amended`, `superseded`, `revoked`); and a half-open validity interval `[valid_from, valid_until)` in ledger sequence numbers.

**Vocabulary — fixed:** `prov:wasRevisionOf` between versions; `prov:Activity` for lifecycle events; `prov:actedOnBehalfOf` for delegation; `prov:SoftwareAgent` for executors. Commitment roles are `soc:debtor`, `soc:creditor`, `soc:antecedent`, `soc:consequent`.

**The shapes must reject, each with a fixture that proves it:**

1. a ratified version with no evidence;
2. a version with no owner on its commitment;
3. a brief change whose actor is not the principal;
4. a ratified version with no source quote, or no checkable rule;
5. a validity interval that is empty or reversed;
6. a revision with no `prov:wasRevisionOf` link to the version it replaces;
7. a consistency level or state outside the lists above.

They must also **accept** a set of valid fixtures covering every state and every consistency level, and an executor change that leaves every validity interval unchanged.

**Validation runs inside the write transaction**, on the record being written and whatever it references. A record that fails is not written, and the error names the shape that failed.

**Measure it.** Report the validation time per write (median and 95th percentile) on the toy episode's volume. There is an approved fallback — Pydantic models with the same field names — but **switching to it is Can's decision, not yours.** Build the Pydantic models anyway (they are the typed interface), keep SHACL as the validator, and report the numbers.

*Your choice, to be confirmed:* the namespace IRI for `soc:`. Put it in one constant and list it in `OPEN_QUESTIONS.md`.

## 7. What the reviewer will check

Claude reviews against this list. It is here so nothing in the review is a surprise.

- Every exit test is real: it can fail, and it fails when the property is broken on purpose.
- No path writes a projection directly, and no path updates or deletes an event.
- A stale ratification can never overwrite: there is no code path where the later write wins.
- Version monotonicity and append-only are enforced by the database, not only by Python.
- Authority checks cannot be bypassed by calling a lower-level function.
- The property test's state machine models conflicts and revisions, not only the happy path.
- The concurrency test uses separate processes, not threads sharing a connection.
- The hash covers every column that matters, and the verifier detects a single altered byte.
- The shapes are the validator in the write path, and each rejection fixture fails for its intended reason only.
- The runtime loader's inability to reach evaluation data is structural, not a convention.
- The segmenter's IDs do not shift when an unrelated section changes.
- Nothing from section 5 was built, and nothing in section 4 was quietly simplified.
- `OPEN_QUESTIONS.md` exists and is honest.
